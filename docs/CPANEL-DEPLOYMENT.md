# استقرار روی سی‌پنل بدون Node.js و ترمینال

بستهٔ فعلی با `composer.lock` موجود به PHP **8.4.1 یا بالاتر**، افزونه‌های موردنیاز
Laravel و MySQL نیاز دارد. حداقل `8.3` در `composer.json` به‌تنهایی کافی نیست؛
چند وابستگی قفل‌شدهٔ Symfony به `8.4.1` نیاز دارند. برای هاست PHP 8.3 باید ابتدا
وابستگی‌ها با همان نسخه حل و دوباره تست شوند؛ بررسی نسخه را دور نزنید.
Node.js و Composer روی دستگاه توسعه یا سیستم ساخت اجرا می‌شوند؛ فایل‌های آماده
روی هاست آپلود می‌شوند. اجرای Node.js، Python یا SSR روی هاست لازم نیست.

## رفتار سئو

PHP در پاسخ اولیه عنوان، توضیحات، canonical، hreflang، Open Graph و JSON-LD را
تولید می‌کند. متن صفحات، مقاله‌ها، خدمات، نمونه‌کارها و لینک‌های داخلی هم با Blade
در بدنهٔ HTML وجود دارند. این محتوا برای کاربران و خزنده‌ها یکسان است و حتی با
JavaScript خاموش قابل‌خواندن است. با اجرای JavaScript، Vue نمای تعاملی را جایگزین
می‌کند. این نمای اولیهٔ PHP یک نمای خواندنی ساده است؛ فرم‌ها و انیمیشن‌های سایت
به JavaScript مرورگر نیاز دارند.

محتوا از همان داده‌های منتشرشده و ترجمه‌شدهٔ کنترلرها می‌آید. تغییر محتوا در پنل
مدیریت نیازی به ساخت مجدد فایل‌های JavaScript یا یک snapshot جداگانه ندارد.

## آماده‌سازی روی دستگاه توسعه

این دستورها روی کامپیوتر توسعه اجرا می‌شوند، نه در سی‌پنل:

```bash
composer install
npm ci
php vendor/bin/pest
npm run build
```

### ساخت خودکار فایل ZIP

بعد از نصب وابستگی‌های محلی، اجرا کنید:

```bash
npm run build:cpanel
```

این دستور هر بار بیلد تازه می‌سازد و خروجی را در
`dist/cpanel/sizdah-cpanel.zip` قرار می‌دهد. به Bash، PHP، Composer، npm، rsync و
zip روی دستگاه توسعه نیاز دارد. `vendor` تولید و فایل‌های `public/build`، فایل‌های
عمومی پنل مدیریت و رسانه‌های `storage/app/public` داخل بسته هستند. وابستگی‌های
توسعهٔ PHP فقط در کپی موقت حذف می‌شوند و `vendor` لوکال تغییر نمی‌کند.

فایل `.env` لوکال، دیتابیس SQLite، نسخه‌های پشتیبان، لاگ‌ها، سشن‌ها، کش‌های محلی،
`public/hot` و `node_modules` وارد بسته نمی‌شوند. داده‌های دیتابیس باید جداگانه
منتقل شوند؛ این ZIP شامل SQL یا حساب مدیر آماده نیست. در به‌روزرسانی سایت موجود،
`.env` و رسانه‌های هاست را حفظ کنید و بسته را بدون بررسی روی آن‌ها بازنویسی نکنید.

فایل `.env.example` داخل ZIP تنظیمات پایهٔ production دارد. برای استقرار اولیه،
از آن `.env` بسازید، دامنه، دیتابیس و SMTP واقعی را وارد کنید و کلید تازه را با
دستور زیر **روی لوکال** تولید و در `APP_KEY` فایل هاست قرار دهید:

```bash
php artisan key:generate --show
```

برای سایت موجود، همان `APP_KEY` قبلی هاست را نگه دارید. روی لوکال برای آپلود
`config:cache`، `route:cache` یا `view:cache` اجرا نکنید؛ این کش‌ها ممکن است مقادیر
و مسیرهای دستگاه توسعه را وارد هاست کنند. اسکریپت بسته‌بندی تست‌ها را اجرا نمی‌کند؛
تست‌ها را جداگانه بررسی کنید.

### آماده‌سازی دستی کپی آپلود

یک کپی جداگانه برای آپلود تهیه کنید. در همان کپی، وابستگی‌های PHP تولید را آماده
کنید و کش‌های مربوط به محیط محلی را پاک کنید:

```bash
composer install --no-dev --optimize-autoloader
php artisan config:clear
php artisan route:clear
php artisan view:clear
php artisan event:clear
```

از `optimize:clear` با تنظیمات دیتابیس لوکال در کپی آپلود استفاده نکنید؛ این دستور
کش برنامه را هم پاک می‌کند و ممکن است به دیتابیس واقعی محیط توسعه متصل شود.

فایل `public/hot` را در کپی آپلود حذف کنید. این فایل مخصوص Vite در محیط توسعه است
و وجودش باعث می‌شود سایت به‌جای فایل‌های ساخته‌شده، سرور توسعه را درخواست کند.
پوشهٔ `public/build` و فایل `manifest.json` داخل آن باید آپلود شوند.
پوشهٔ `vendor` هم باید همراه پروژه باشد؛ `node_modules` و `bootstrap/ssr` لازم نیستند.
کش‌های محیط محلی در `bootstrap/cache` و `storage/framework/views` را آپلود نکنید.

نسخهٔ PHP و افزونه‌های سیستم ساخت باید با هاست سازگار باشند. پوشه‌های
`storage` و `bootstrap/cache` باید برای PHP هاست قابل نوشتن باشند.

## تنظیم در سی‌پنل

1. پروژه را خارج از پوشهٔ عمومی سایت قرار دهید و document root دامنه را روی
   پوشهٔ `public` پروژه بگذارید. اگر سی‌پنل این امکان را نمی‌دهد، از پشتیبانی برای
   تنظیم document root کمک بگیرید؛ ریشهٔ پروژه و `.env` نباید عمومی شوند.
   فایل مخفی `public/.htaccess` هم باید منتقل شود؛ Apache به فعال بودن
   `mod_rewrite` و اجازهٔ خواندن قواعد `.htaccess` برای مسیرهای Laravel نیاز دارد.
2. دیتابیس و کاربر MySQL را در سی‌پنل بسازید و مقدارهای `DB_*` را در `.env` تنظیم
   کنید. در استقرار اولیه، SQL آماده‌شده در محیط محلی را با phpMyAdmin وارد کنید.
   برای سایت موجود، داده‌های واقعی را حفظ کنید و تغییرات ساختار را جداگانه اعمال کنید.
3. در `.env` تنظیم‌های زیر را قرار دهید و `APP_KEY` معتبر پروژه، آدرس واقعی سایت،
   مشخصات دیتابیس و SMTP را وارد کنید:

   ```dotenv
   APP_ENV=production
   APP_DEBUG=false
   APP_URL=https://example.com
   INERTIA_SSR_ENABLED=false
   QUEUE_CONNECTION=sync
   ```

   `sync` اعلان‌های فرم تماس را در همان درخواست PHP ارسال می‌کند و به queue worker
   دائمی نیاز ندارد. ارسال ممکن است به‌اندازهٔ پاسخ SMTP زمان ببرد.
4. برای رسانه‌های آپلودشده، لینک `public/storage` به `storage/app/public` باید
   برقرار باشد. در نبود ترمینال، از امکانات مدیریت فایل هاست یا پشتیبانی برای
   ایجاد این symlink استفاده کنید.
5. اگر نسخهٔ قبلی کش تنظیمات دارد، فایل تولیدشدهٔ `bootstrap/cache/config.php`
   را با File Manager حذف کنید تا `.env` جدید خوانده شود. کش‌های تولیدشدهٔ Blade
   در `storage/framework/views` هم باید پس از جایگزینی قالب‌ها پاک شوند.

راه‌اندازی اولیهٔ دیتابیس، ارتقای ساختار آن و تنظیم دسترسی فایل‌ها همچنان لازم‌اند؛
حذف نیاز به Node.js جایگزین این مراحل نمی‌شود. انتشار زمان‌بندی‌شدهٔ محتوا به cron
اجرای scheduler نیاز دارد؛ بدون cron، محتوا را در پنل به‌صورت دستی منتشر کنید.

## بررسی پس از آپلود

- با View Source صفحات، وجود `main`، `h1`، متن واقعی مقاله و لینک‌های داخلی را
  بررسی کنید؛ صرفاً وجود متن داخل `data-page` کافی نیست.
- با JavaScript خاموش، متن‌ها و لینک‌های معمولی باید قابل استفاده باشند.
- با JavaScript روشن، ظاهر Vue و رفت‌وآمد داخلی صفحات و به‌روزرسانی متاتگ‌ها را
  بررسی کنید.
- `/robots.txt`، `/sitemap.xml` و `/sitemap-fa.xml` باید پاسخ معتبر بدهند.
- آدرس مقاله یا پروژهٔ ناموجود باید HTTP 404 و `noindex` بدهد.

این تغییر امکان خواندن محتوا بدون اجرای JavaScript را فراهم می‌کند؛ رتبه یا زمان
ایندکس شدن در موتور جست‌وجو را تضمین نمی‌کند.
